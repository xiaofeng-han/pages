  1. Throttling and routing, used as the incident lever

    Built the gateway's throttling and routing features, then used them on call to shed load in front of struggling services.

    Throttle and route stages. Rate limiting, quota, routing, incident response.

  2. Shadow-mode verification for moving authorization into the gateway

    Let service teams prove the gateway would send the same authorization request they did, before they switched. I onboarded 2 teams directly; about 15 more did it on their own.

    Authorize stage. Authorization, IAM, shared SDK, migration.

    Read the detailsHide the details
    The problem
    Services authorized requests themselves by calling Identity through a shared SDK, so the gateway never saw what they sent. Teams wanted to move authorization into the gateway but needed evidence that nothing would change.
    What I built
    A change to the Identity SDK: in verification mode it writes the authorization request it sent into an internal response header. The gateway reads that header, strips it before replying to the caller, and compares it with the request the gateway generates itself.
    The comparison
    JSON bodies are compared as nested maps. Known-variable fields such as timestamps are excluded by explicit field path, and list order is ignored only where the business meaning doesn't depend on it. Match, mismatch, and missing header each produce their own logs and metrics. The downstream allow or deny decision always stands.
    How it shipped
    I submitted the SDK pull request, ran a test build in pre-production with a canary service simulating downstream behavior, and supported the first 2 teams through migration. About 15 more teams used it to complete theirs.

  3. An allowlist sandbox for team-written expressions

    Replaced a blacklist with an explicit capability allowlist, so Groovy expressions written by service teams can read request data but never change it.

    Context expression stage. Sandboxing, policy review, configuration distribution.

    Read the detailsHide the details
    The problem
    Internal service teams write and audit Groovy expressions that compute request context. The gateway has to let them read what they need without modifying request state or reaching unsafe capabilities.
    Why an allowlist
    I started with a blacklist and found it couldn't reliably cover every mutation path. So I scanned existing expressions for their access patterns, reviewed the JDK classes they used, and moved to explicit allow rules.
    The rules
    Whole-class access only for classes whose source we control and have verified to be read-only; selected methods for everything else. Maps allow reads and iteration (get, forEach) but block put, remove, clear, and updates. No reflection. The rules apply to nested objects too.
    Running it
    The gateway team owns the global allowlist and reviews extension requests. Approved changes go out through the configuration service and refresh into a local cache every 5 minutes, so the request path has no remote dependency and nothing needs a redeploy. Unit and environment tests confirm expressions can no longer modify requests through the identified APIs.

  4. Outcome-based log routing, with 80% fewer bytes to the log service

    Proposed, built, and rolled out request-level log routing: error-path logs go to the searchable log service, everything else to object storage.

    Logging, after the response. Observability, cost, Java logging internals.

    Read the detailsHide the details
    The problem
    The gateway produced more log data than the logging service could comfortably ingest. Conventional reductions, like compacting stack traces and trimming tracing fields, weren't enough.
    What I built
    Each request buffers its already-formatted log lines. When the request finishes, its outcome decides where they go: internal-error and user-error requests go to the log service, where they can be queried and aggregated; the rest go to cheaper object storage.
    Inside the stack
    I extended the existing logging library through its Java SPI with a custom async appender, keeping the structured JSONL output and MDC context unchanged. A request-scoped marker carries the buffer across thread hand-offs and is always cleared before a worker thread returns.
    Safeguards
    The first design was sized from the log-size distribution, per-service in-flight limits, and the gateway's memory budget. As traffic grew I added hard limits of 300 lines and 5 minutes per request; past either, the request flushes and falls back to real-time logging.
    Result
    80% less data sent to the log server, measured in bytes in both pre-production and production.

  5. Java 8 to 17, then 21 and 25, rolled out region by region

    Led the worldwide runtime migration with staged bake periods and a clean rollback path, then carried the codebase on to Java 21 and 25.

    Runtime under every stage. Change management, staged rollout, JVM diagnostics.

    Read the detailsHide the details
    The plan
    Straight from 8 to 17, skipping 11: 17 was the newer LTS and the base for later Dropwizard 3 and Jetty 10 upgrades. I owned code changes, dependency compatibility, build-service configuration, testing, deployment, monitoring, and customer feedback.
    The blocker
    A required third-party dependency used JDK-internal sun.* APIs that don't work on 17, and waiting for an upstream fix would have stalled the migration. I decompiled the class, reimplemented it on supported APIs, swapped it in with the Maven Shade Plugin, and tested the final JAR.
    The rollout
    1 week in pre-production, 2 weeks in smaller production regions, then worldwide, watching CPU, memory, thread pools, error rates, traffic, and customer feedback. The JDK change shipped apart from feature releases so a rollback would never pull unrelated work.
    After launch
    Some customers still used legacy TLS cipher suites. With Security Board approval I added a time-boxed exception in the global configuration and removed it once they upgraded. Later, on Java 21 and 25, I diagnosed virtual-thread pinning with Java Flight Recorder.
